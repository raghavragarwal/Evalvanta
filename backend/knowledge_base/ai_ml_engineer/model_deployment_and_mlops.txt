Model Deployment and MLOps

A model that performs well in a notebook is not the same thing as a model that performs well in production, and the gap between the two is where most of the practical difficulty of applied machine learning actually lives. Training-serving skew occurs when the features computed at training time differ, even subtly, from the features computed at inference time -- for example, a feature engineered from a batch job that has access to a full day's data, served at inference time from a streaming pipeline that only has a partial window. This kind of skew is dangerous precisely because it doesn't show up as an error; the model simply performs worse in production than its offline metrics predicted, often without an obvious cause until someone audits the actual feature values flowing through each path.

Model monitoring in production needs to track more than just uptime and latency. Data drift refers to a shift in the distribution of input features over time -- for example, a fraud model trained on pre-pandemic transaction patterns encountering a very different distribution of transaction types afterward. Concept drift refers to a shift in the actual relationship between inputs and outputs -- the same input features now correspond to a different correct output than they used to. Both degrade model performance over time even if nothing about the model itself has changed, which is why production ML systems typically monitor prediction distributions and, where ground truth becomes available with some delay, actual accuracy metrics over time, rather than assuming a model's performance is static once deployed.

The choice between batch and real-time inference is a system design decision with real consequences. Batch inference (scoring a large set of examples on a schedule and storing the results) is simpler to build, easier to make efficient through vectorization, and tolerant of slower individual predictions, but it means predictions can be stale by the time they're used. Real-time inference (scoring on demand as requests arrive) gives fresh predictions but adds latency requirements and operational complexity to the serving path -- the model now needs to be part of a live request path with its own uptime and latency SLAs, rather than an offline job that can be retried or delayed without directly affecting users.

A/B testing a new model against the current production model is the standard way to validate that offline improvements actually translate into better real-world outcomes, because offline metrics can be misleading -- a model can have better accuracy on a held-out test set while performing worse on the actual business metric that matters, if the test set doesn't perfectly represent production traffic or if accuracy isn't perfectly aligned with the business objective. Shadow deployment, where a new model receives live production traffic and its predictions are logged but not actually acted upon, is a lower-risk way to gather that same real-world performance signal before committing to a full A/B test or rollout.

Retraining pipelines need a clear answer to two questions: how often should the model retrain, and what triggers a retrain outside of that schedule. Fixed-schedule retraining (weekly, monthly) is simple but can be wasteful if the underlying distribution is stable, or dangerously slow to react if it's not. Trigger-based retraining, driven by monitored drift metrics crossing a threshold, reacts faster to genuine distribution changes but requires the monitoring infrastructure to be reliable enough that a spurious drift signal doesn't trigger unnecessary retraining churn.
