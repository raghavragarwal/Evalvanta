Scalability and System Design

Vertical scaling (adding more CPU, memory, or disk to a single machine) is the simplest way to handle increased load, but it has a hard ceiling and a single point of failure: the one machine. Horizontal scaling (adding more machines and distributing load across them) removes that ceiling but introduces new problems that don't exist on a single machine -- how do requests get routed to the right instance, how does state get shared or replicated across instances, and how does the system behave when one of those instances fails. A backend engineer choosing between the two is really choosing how much operational complexity to take on in exchange for how much headroom they need.

Load balancing is the mechanism that makes horizontal scaling work in practice. A load balancer distributes incoming requests across a pool of backend instances, commonly using round-robin, least-connections, or consistent-hashing strategies. Consistent hashing is particularly relevant when backend instances hold in-memory state (like a cache) tied to a specific key -- it minimizes how many keys need to be remapped when an instance is added or removed, compared to naive modulo-based hashing where nearly every key remaps on any change to the pool size.

Message queues decouple the producer of work from the consumer of work, which has two major benefits: it smooths out traffic spikes (the queue absorbs a burst of requests that a synchronous system would reject or time out on), and it lets producer and consumer scale independently and fail independently. A queue-based architecture also changes the failure mode of a system: instead of a slow downstream dependency directly slowing down or failing the request that depends on it, that request can enqueue work and return immediately, with the actual processing happening asynchronously. The tradeoff is that the caller no longer gets an immediate result, and the system needs a way to communicate eventual completion or failure back to whoever is waiting on it.

Circuit breakers protect a system from cascading failure. When a downstream service starts failing or timing out, naively continuing to send it traffic wastes resources on requests that are likely to fail anyway, and can make the downstream service's recovery harder by keeping it under load. A circuit breaker tracks the failure rate of calls to a dependency and, once it crosses a threshold, "opens" -- failing fast locally without even attempting the call -- for a cooldown period, then allows a small number of test requests through to check whether the dependency has recovered before fully closing again. This pattern trades a small amount of availability (some requests fail immediately that might have otherwise succeeded) for a much larger gain in resilience (the failing dependency isn't further overwhelmed, and the calling service isn't blocked waiting on doomed requests).

Observability -- logging, metrics, and distributed tracing -- becomes essential once a system is decomposed into multiple services, because a single user-facing request may now touch many services, and a failure or slowdown in any one of them can be the root cause. Distributed tracing assigns a unique trace ID to a request at the point it enters the system and propagates that ID through every downstream call, so that all the logs and spans related to a single request can be reconstructed after the fact into a single timeline, even though the work happened across many independent processes.
