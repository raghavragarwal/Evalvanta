Databases and Data Consistency

Choosing between a relational and a non-relational database is fundamentally a choice about which invariants the database will enforce for you versus which ones your application code must enforce itself. Relational databases enforce a schema, foreign key relationships, and transactional guarantees at the storage layer. This is valuable when data has clear structure and strong consistency requirements -- financial ledgers, inventory counts, anything where two related pieces of data must never be observed in an inconsistent state. Document and key-value stores trade that structural rigidity for flexibility and horizontal scalability, which suits data that is naturally hierarchical, high in write volume, or does not benefit from cross-record joins, such as session state or event logs.

Transactions and the ACID properties (Atomicity, Consistency, Isolation, Durability) describe the guarantees a relational database makes about grouped operations. Atomicity ensures a multi-step operation either fully completes or fully rolls back; a partially applied bank transfer that debits one account without crediting another would violate atomicity. Isolation determines how concurrent transactions see each other's uncommitted changes -- the isolation level is a deliberate trade-off between consistency guarantees and throughput. Serializable isolation, the strongest level, behaves as though transactions ran one at a time, but it comes at a real performance cost as concurrency increases; many production systems choose a weaker level like Read Committed and add explicit locking only where correctness genuinely requires it.

In distributed systems, the CAP theorem forces a choice: when a network partition occurs, a system can preserve either Consistency (every read sees the latest write) or Availability (every request gets a response), but not both. Systems designed for high availability under partition (such as many NoSQL stores) instead offer eventual consistency: writes propagate asynchronously, and reads may briefly return stale data, but all replicas converge given enough time without further writes. Backend engineers need to understand which consistency model a given data store actually offers, because application logic that assumes strong consistency will produce subtle bugs -- race conditions that only appear under real production load -- if the underlying store is only eventually consistent.

Indexing is the primary lever for read performance in any database. A B-tree index on a column lets the database locate matching rows in logarithmic time instead of scanning the full table, but every index also slows down writes, since each insert or update must maintain the index alongside the underlying table. Composite indexes (spanning multiple columns) are only useful for queries that filter on a matching left-to-right prefix of the indexed columns; an index on (user_id, created_at) speeds up a query filtering on user_id alone or on both columns together, but not a query filtering on created_at alone. This makes index design inseparable from understanding the actual query patterns the application will issue -- indexing "just in case" without a real query to justify it usually costs more in write overhead than it ever saves in read performance.

Caching sits on top of the database to absorb read load, but introduces its own hard problem: cache invalidation. A cache-aside pattern (read from cache, on miss read from the database and populate the cache) is simple but leaves a window where the cache can serve stale data after an underlying write. Systems with strict freshness requirements often invalidate or update the cache synchronously as part of the write path, at the cost of added write latency and complexity.
